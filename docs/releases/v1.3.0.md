# AgentCore OS v1.3.0

`v1.3.0` is the current recommended public release of AgentCore OS.

This release does not expand the product by adding more standalone apps. It tightens the existing local-first system: version alignment, API safety boundaries, runtime defaults, media-processing guardrails, and the documented direction for the next stable line.

## Release Positioning

The main goal of `v1.3.0` is to make the current product surface safer and more coherent before deepening the next set of workflows.

Compared with `v1.2.0`, this release focuses on:

- aligning package, Tauri, and public documentation versions around `1.3.0`
- adding a local API safety boundary for high-risk execution, LLM, media, and credential-related endpoints
- supporting `AGENTCORE_API_AUTH_TOKEN` as an additional local API protection layer
- changing the default AgentCoreOS Runtime permission mode from `workspace-write` to `read-only`
- protecting local media processing from arbitrary filesystem reads
- keeping the browser workflow, publish queue, workflow state, and executor-session regression gates intact
- reducing the initial browser bundle by lazy-loading app windows

## What Changed

### 1. Version and documentation alignment

The current public entry points now point to `v1.3.0`:

- `package.json`
- Tauri desktop configuration
- README
- command-line installation guide
- documentation index
- early-access distribution guide
- roadmap

Historical `v1.2.0` release notes remain in place as release history.

### 2. Local API safety boundary

High-risk API routes now reject non-local requests by default.

This covers execution, model proxying, media processing, publish configuration mutation, and dispatch surfaces that should not be reachable as open remote-control endpoints.

When `AGENTCORE_API_AUTH_TOKEN` is configured, local requests must also provide either:

- `Authorization: Bearer <token>`
- `X-AgentCore-Token: <token>`

### 3. Safer runtime defaults

AgentCoreOS Runtime execution now defaults to `read-only` instead of `workspace-write`.

Users can still opt into broader permission modes when a workflow requires write access, but the default startup posture is more conservative.

### 4. Media processing guardrails

Local ffmpeg processing now only accepts files saved through the AgentCore upload directory.

Remote `fileUrl` inputs require a configured runtime engine instead of being silently treated as local ffmpeg inputs.

### 5. Browser bundle reduction

App windows are now lazy-loaded from the app registry.

The verified production build reduced the `/` route from roughly `252 kB / 357 kB First Load JS` to `74.6 kB / 181 kB First Load JS`.

## Current Product Direction

The near-term direction is not to add more app count.

The default priorities are:

1. deepen the content workflow: `Creator Radar -> Content Repurposer -> Publisher`
2. deepen the sales workflow: `Deal Desk -> Email Assistant -> Personal CRM`
3. make scenario packs runnable, not only installable
4. continue converging executor, session, audit, and retained-asset models

## Verification

The following verification was run for this release line:

```bash
npm run test:stability
npm run runtime:doctor
```

`npm run test:stability` covers:

- core workflow regression
- publish regression
- lint
- production build

`runtime:doctor` confirmed Node.js, ffmpeg, and local storage on the current machine. It still reported that the AgentCoreOS Runtime binary and Docker were not configured locally. That means the browser line is ready, while full desktop runtime execution still requires configuring `AGENTCORE_CLAW_CODE_BIN` or adding the runtime binary to `PATH`.
