# AgentCore OS 可控执行开发计划书

日期：2026-09-28  
基线：GitHub `main` `b0d8295`（2026-09-13），`package.json` 版本 `1.3.0-beta.1`  
读者：项目维护者  
地位：下一阶段只按这份计划做。仓库里更早的「32 个应用」「ActionOS 已原子回写 ERP」不作为本阶段目标。

## 1. 要做成什么

一次执行的步骤顺序、允许的工具、该停下来等人的位置，都由剧本事先写死。模型不能改顺序。写出去给人用的结果，必须先通过该步的输出契约；需要人工复核的结果，在批准之前不得成为业务资产。

这句话对应仓库里已经存在的执行器，不是新造一个系统。

过程可控的现成位置：

- 剧本目录：`src/lib/executor/playbooks/catalog.ts`
- 执行与停点：`src/lib/executor/step-executor.ts`
- 已登记、因此跑得到的剧本：`sales-pipeline-v1`、`support-resolution-v1`

结果可控的现成位置：

- 输出对不上 `outputSchema` 时，该步被判失败：`step-executor.ts` 里的 `validateControlledOutput`
- `when: "after_approval"` 且未批准时，写回被跳过，回执为 `Skipped because output is not approved`：`src/lib/executor/runtime/writeback.ts`

## 2. 现在的基线

GitHub `main` 与本机已提交的 `HEAD` 是同一个提交。最新 Release 仍是 2026-05-23 的标签 `v1.4.0`，该标签里的 `package.json` 版本是 `1.3.0`。`main` 比这个标签多 476 个提交，对外版本号对不上。

两条剧本的步骤和写回条件如下。

`sales-pipeline-v1`（`src/lib/executor/playbooks/sales-pipeline.ts`）：

| 步骤 | 审批 | 写回 |
| --- | --- | --- |
| `intake` | 否 | `workflow_run`，`on_success` |
| `qualify` | 否 | `sales_asset`，`on_success` |
| `draft_outreach` | 否 | `draft`，`on_success` |
| `human_review` | 是 | `workflow_run`，`after_approval` |
| `writeback` | 是 | `sales_asset`、`knowledge_asset`、`workflow_run`，`after_approval` |

`support-resolution-v1`（`src/lib/executor/playbooks/support-resolution.ts`）同样是五步：`intake`、`classify`、`draft_reply`、`human_review`、`writeback`。`classify` 在批准前写入 `support_asset`，`draft_reply` 在批准前写入 `draft`。终稿三项目标才是 `after_approval`。

因此执行器会在复核步停住，但业务资产和草稿在复核之前已经落地。这是本阶段要收紧的缺口。

界面还没接到这条执行器上。`DealDeskAppWindow.v2.tsx` 用 `startWorkflowRun` 走另一套本地工作流。`EnterpriseActionCockpitAppWindow.v2.tsx`、`src/lib/executor/playbooks/supply-chain-replenishment.ts`、`src/lib/executor/tools/erp-tools.ts`、`agentcore-erp/` 都是本机未提交文件。驾驶舱的启动按钮用定时器改本地状态，批准按钮弹出写死单号。供应链剧本不在 `catalog.ts` 里。这些不进入本阶段。

运行控制台 `ClawRuntimeConsoleAppWindow.tsx` 已经调用：

- `GET /api/runtime/executor/controlled-runs`（当前这个路由文件只有列表，没有创建运行的 POST）
- `/api/runtime/executor/controlled-runs/:runId/resume`
- 同路径下的 `retry` 与 `trace-artifact`

本阶段的界面只延伸这一处。

## 3. 做完时必须能演示的事

一个人在运行控制台启动 `sales-pipeline-v1`，用一份固定夹具输入，不依赖真实客户数据：

1. 运行按 `intake` → `qualify` → `draft_outreach` 走完，并在 `human_review` 停住，状态为 `awaiting_approval`。
2. 停住时，销售资产库和知识资产库里没有这条运行的终稿。`qualify` 不再写入 `sales_asset`。
3. 若 `draft_outreach` 仍写入草稿，该草稿的状态只能是待复核，不能带已发送或已批准标记。
4. 把 `draft_outreach` 的输出改到不符合 `outputSchema`，该步失败，不产生待复核草稿。
5. 在 `human_review` 驳回后，`writeback` 不执行，`sales_asset` 与 `knowledge_asset` 不出现这条运行的新终稿。
6. 批准后续跑 `writeback`，只写入批准后的正文，控制台能打开这次 trace。
7. 用 `support-resolution-v1` 重复第 2、5 条：`classify` 不再提前写 `support_asset`，驳回后不写终稿。

七条都有自动测试。第 1 条和第 6 条另外留一次手工记录：控制台屏幕上能看见停住和批准后的 trace。手工记录写在 `docs/可控执行-演示记录.md`，只记日期、输入夹具名、运行 id、停住的步骤、驳回与批准各一次的资产 id。不写节省金额，不写客户名。

## 4. 本阶段不做

- 不新增应用窗口，不改 32 个窗口的 v2 视觉。
- 不把供应链剧本登记进 `catalog.ts`，不提交本机的驾驶舱、`erp-tools.ts` 和 `agentcore-erp/`。这些文件保持未跟踪，直到本计划七条演示通过之后另作决定。
- 不新写发布门禁、playbook 变更交接、trace fixture 治理脚本。
- 不重写现有几百份 Markdown。只改 README 开头一节，并新增本计划与演示记录。
- 不接真实 ERP、ITSM、邮件外发。写回目标仍是现有的 `sales_asset`、`support_asset`、`knowledge_asset`、`draft`、`workflow_run`。
- 不改许可证，不把星标或克隆数列为本阶段指标。

## 5. 规则

1. 只有 `catalog.ts` 里的剧本可以被说成「能执行」。
2. `workflow_run` 可以在步骤成功时写入，它是过程记录。
3. `sales_asset`、`support_asset`、`knowledge_asset` 只允许 `when: "after_approval"`。
4. `draft` 若在批准前写入，存储状态必须是待复核。发送、批准、回写一类字段在待复核状态下不得为真。
5. 输出契约校验失败的步骤，不得调用 `writeControlledStepAssets`。这条执行器里已经如此，测试要锁住它。
6. 界面上的「已写回」「已批准」只能来自写回回执或审批记录，不能来自按钮点击后的本地文案。

## 6. 工作顺序

按一个人维护来排。日期是建议，退出条件到了才能进入下一步。建议从 2026-09-29 起，三周内做完；某一周测试没过就停在那一周，不并行加功能。

### 第 1 周：锁住结果门禁

改两个剧本，并先写会失败的测试。

文件：

- `src/lib/executor/playbooks/sales-pipeline.ts`
- `src/lib/executor/playbooks/support-resolution.ts`
- `src/__tests__/lib/executor/playbooks/sales-pipeline.test.ts`（若断言了旧的 `writesTo`，一起改）
- `src/__tests__/lib/executor/playbooks/support-resolution.test.ts`
- 新增 `src/__tests__/lib/executor/runtime/writeback-approval-gate.test.ts`

具体改动：

- `qualify` 的 `writesTo` 改为 `workflow_run` / `on_success`。删掉这一步的 `sales_asset`。
- `classify` 的 `writesTo` 改为 `workflow_run` / `on_success`。删掉这一步的 `support_asset`。
- `draft_outreach`、`draft_reply` 可以保留 `draft` / `on_success`。在 `writeDraft` 的写入载荷里确认状态是待复核。若现有草稿类型没有这个状态，就在草稿记录上增加 `approvalState: "pending_review"`，并让读草稿的界面能看见这三个字。不在本周做发送按钮。
- `human_review` 与 `writeback` 的 `after_approval` 保持不动。

测试必须覆盖：

- 未批准时调用 `writeControlledStepAssets`，`sales_asset` 与 `knowledge_asset` 的回执是跳过，存储里没有新终稿。
- `qualify` 成功后只有 `workflow_run` 回执，没有 `sales_asset`。
- `outputSchema` 校验失败时，`writeControlledStepAssets` 不被调用。
- 驳回 `human_review` 后，`writeback` 步骤不处于 `completed`。

本周退出条件：上述测试通过，且 `npx tsc --noEmit` 对改动文件无新错误。不要求全仓库 140 个测试文件在本周重跑；周末跑一次 `npm run test:controlled-runtime` 里与 sales、support、writeback、step-executor 相关的已有测试。全量失败若来自未改动的发布门禁，记在演示记录草稿里，不在本周修门禁。

### 第 2 周：从控制台真正跑起来

要补上的行为：

- 资产区若控制台还没有，就在同一窗口加一段文字：最近一条写回回执的 `target`、`ok`、`summary`。数据来自运行记录里已保存的回执。没有回执就显示「尚无写回」。

## 7. 风险

- `test:controlled-runtime` 里大量测试锁定了旧的 `writesTo`。第 1 周若失败，只改断言到新规则，不放宽门禁去迁就旧行为。
- 草稿类型若被多个窗口直接当「已可发送」使用，加上 `approvalState` 后，那些窗口可能仍显示旧文案。本阶段不逐个改窗口；演示记录里写明哪些窗口还没读这个字段。
- 控制台若今天的 POST 只做查询、创建逻辑散落在 `stream/route.ts`，第 2 周可能比预想多触一个文件。仍然只打通夹具启动，不接开放式聊天输入。
- 本机未提交的 ERP 文件容易在一次大提交里被带上。每批提交前用 `git status` 确认没有 `agentcore-erp/`、`erp-tools.ts`、`supply-chain-replenishment.ts`、`EnterpriseActionCockpitAppWindow.v2.tsx`。
